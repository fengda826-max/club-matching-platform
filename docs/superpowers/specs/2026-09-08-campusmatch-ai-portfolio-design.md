# CampusMatch AI 求职作品设计

## 1. 项目定位

### 1.1 目标岗位

本项目只面向云解决方案、售前架构及 AI 应用解决方案类岗位，重点展示以下能力：

- 从业务场景中识别客户需求并确定交付边界。
- 将 AI、Web 和云基础设施组合成可落地的解决方案。
- 对模型输出进行验证、约束、评估和降级。
- 根据业务阶段在成本、复杂度、可靠性之间做取舍。
- 使用清晰的文档、在线演示和架构说明完成方案表达。

本项目不以算法研究、复杂平台研发或生产级微服务为目标。

### 1.2 一句话介绍

CampusMatch AI 是面向高校团委集中招新场景的 AI 云解决方案 PoC，通过可信推荐、社团知识问答、加入意向和运营分析，降低学生的信息筛选成本与校方的招新运营成本。

### 1.3 作品交付物

- 一个公网可访问的在线演示。
- 一个包含源码、部署配置和完整说明的 GitHub 仓库。
- 一份可重复生成的 AI 评估报告。
- README 中的业务分析、架构图、成本估算和设计取舍。
- 一套五分钟面试演示脚本。

不制作单独的 PPT 或完整生产架构方案。

## 2. 客户与业务场景

### 2.1 客户定义

PoC 客户是一所高校的团委或学工部门。学校拥有数十至数百个社团，每年开学季集中招新。

当前招新信息主要分散在海报、群聊和表格中，导致：

- 学生难以快速比较社团并判断是否适合自己。
- 社团负责人重复回答活动时间、门槛、费用等问题。
- 校方缺少统一、可信的社团信息源。
- 校方无法观察学生需求、咨询热点和招新转化。

### 2.2 用户角色

#### 学生

- 浏览和筛选社团。
- 使用表单或自然语言描述个人偏好。
- 获得可解释的推荐结果。
- 基于权威社团资料继续咨询。
- 提交匿名加入意向并获取官方联系方式。

#### 社团负责人

- 维护社团介绍、活动时间、门槛、费用和招新状态。
- 使用 AI 辅助生成内容，但在发布前人工确认。
- 减少重复咨询。

PoC 不单独实现社团负责人账号，其管理能力统一由管理员演示账号呈现。

#### 校方管理员

- 管理权威社团数据。
- 查看推荐、咨询、意向和 AI 服务指标。
- 根据热门兴趣与供给差距调整招新运营策略。

### 2.3 核心业务闭环

```text
学校维护权威社团数据
→ 学生填写偏好或自然语言需求
→ 系统过滤时间、地点、费用和技能等硬约束
→ 系统计算可解释的规则分数
→ AI 为候选结果生成推荐解释
→ 学生咨询并提交加入意向
→ 管理员观察需求与转化数据
→ 下一轮调整社团信息和招新策略
```

### 2.4 PoC 范围

必须交付：

- 社团信息查询和受保护的管理操作。
- 表单与自然语言两种偏好输入。
- 规则过滤、规则评分与 AI 推荐解释。
- 基于社团数据的流式问答和信息引用。
- 匿名加入意向。
- 业务与 AI 服务运营指标。
- AI 输出验证、超时处理和规则降级。
- Docker Compose、Nginx 和腾讯云轻量服务器部署。

明确不做：

- 完整用户注册和校园统一身份认证。
- 支付、面试排期、复杂审批和通知工作流。
- 社团日常活动或成员管理。
- 多学校租户系统。
- 自训练推荐模型。
- 微服务、Kubernetes 或独立生产架构实现。

## 3. 产品设计

### 3.1 首页

首页清楚表达三类客户价值：学生提高选择效率、社团减少重复咨询、校方获得需求和转化数据。技术架构不占用普通用户的主要界面。

### 3.2 社团大厅

保留搜索、分类和标签筛选，并增加：

- 活动时间。
- 每周投入时间。
- 校区或地点。
- 费用。
- 技能门槛。
- 当前是否开放招新。

这些字段同时作为学生决策依据和规则推荐输入。

### 3.3 智能匹配

支持两种输入：

- 表单输入兴趣、目标、技能、时间和预算。
- 自然语言输入个人情况，由 AI 提取结构化偏好。

自然语言提取结果必须先展示给用户确认，然后才进入推荐。

结果展示：

- 总匹配分和各维度分数。
- AI 生成的个性化理由。
- 推荐所引用的社团字段。
- 可能不适合的条件。
- `AI 增强推荐` 或 `规则降级推荐` 状态。
- 加入意向入口。

### 3.4 AI 问答

- 从数据库检索与问题相关的社团记录。
- 只把相关记录交给模型，不发送完整数据库。
- 使用 SSE 逐步显示回答。
- 展示引用社团、响应时间和模型信息。
- 资料不足时明确回答“当前资料没有说明”。
- 模型失败时展示结构化搜索结果。

### 3.5 管理与运营

业务指标：

- 社团数量。
- 推荐使用次数。
- 加入意向次数。
- 推荐到意向的转化率。
- 热门兴趣。
- 需求较高但供给不足的类别。

AI 指标：

- 调用次数和成功率。
- 平均响应时间。
- 结构化输出失败次数。
- 规则降级次数。
- Token 用量和估算费用。

公开访问者可以查看脱敏后的演示指标；社团写操作需要管理员登录。

## 4. AI 方案

### 4.1 职责边界

AI 负责：

- 将自然语言需求提取为结构化偏好。
- 为已经选出的候选社团生成个性化解释。
- 基于检索到的权威社团资料生成自然语言回答。

确定性系统负责：

- 时间、校区、费用和技能等硬约束。
- 推荐分数计算。
- 数据权限和输入验证。
- 社团 ID、分数范围、引用和输出结构校验。

### 4.2 推荐流程

```text
用户输入
→ AI 提取结构化偏好
→ Schema 校验与用户确认
→ 硬约束过滤
→ 规则评分
→ 选择候选社团
→ DeepSeek V4 生成解释和注意事项
→ 输出与事实校验
→ 返回 AI 增强或规则降级结果
```

默认评分权重：

- 兴趣匹配：40%。
- 参与目标：25%。
- 时间匹配：20%。
- 技能与门槛：15%。

评分权重集中配置并由单元测试覆盖。AI 不得修改规则分数。

### 4.3 模型网关

实际演示使用现有 DeepSeek V4 API，并保留统一 Provider 接口：

```text
AIService
└── ModelGateway
    ├── DeepSeekProvider
    ├── TencentTokenHubProvider（可选适配）
    └── RulesOnlyFallback
```

模型网关负责配置、鉴权、超时、重试、错误分类、Token 统计、延迟统计和供应商隔离。腾讯云 TokenHub 只作为可替换 Provider 与选型说明，不是本期必须购买或启用的资源。

### 4.4 可靠性与安全

- 使用运行时 Schema 校验 AI JSON。
- 验证推荐社团真实存在且不重复。
- 拒绝超出范围的分数和字段。
- 推荐理由只能引用候选社团已有事实。
- 限制用户输入、社团资料和对话历史长度。
- 清洗或隔离社团资料中的提示词式指令。
- 模型超时或输出无效时返回规则结果。
- 不在日志中保存完整用户输入或敏感联系方式。
- 浏览器取消 SSE 后同步终止上游请求。

### 4.5 AI 评估

使用固定 JSON 数据集和脚本生成 Markdown 报告。初始评估集包括：

- 20 条学生偏好。
- 20 个常见社团咨询问题。
- 5 个资料中没有答案的问题。
- 5 个提示词攻击或越界问题。

报告指标：

- 结构化输出成功率。
- 推荐硬约束违反率。
- 回答事实一致率。
- 无依据回答率。
- 平均和 P95 响应时间。
- 规则降级成功率。
- 平均 Token 和估算成本。

所有作品和简历中的数字必须来自实际测试结果。

## 5. 技术架构

### 5.1 应用架构

继续使用模块化单体：Vue 3 前端、Express 后端、Prisma 和 SQLite。两天内不进行与作品目标无关的大规模目录重构。

后端职责划分：

```text
routes
├── clubs
├── matching
├── chat
├── intents
├── analytics
└── auth

services
├── ClubService
├── RecommendationService
├── RuleMatchingService
├── ChatService
├── IntentService
└── AnalyticsService

ai
├── ModelGateway
├── DeepSeekProvider
├── PreferenceExtractor
├── ExplanationGenerator
└── OutputValidator
```

### 5.2 实际云上部署

```text
用户浏览器
    ↓
腾讯云轻量应用服务器
    ↓
Nginx
    ├── Vue 静态文件
    └── /api → Node.js 服务
                    ├── SQLite 持久卷
                    └── DeepSeek V4 API
```

Docker Compose 管理 Nginx 和应用服务。部署必须包括：

- 环境变量保存密钥。
- 腾讯云安全组只开放必要端口。
- 应用健康检查。
- SQLite 数据持久卷和定时备份。
- 日志轮转。
- 可重复执行的部署说明。

PoC 不实际引入云数据库、负载均衡、缓存、消息队列或容器集群。

README 只说明三项演进触发条件：

- 单机 CPU 或并发成为瓶颈后再增加负载均衡与多实例。
- 数据可靠性或并发写入成为问题后再迁移托管数据库。
- 非结构化资料显著增长后再引入对象存储和向量检索。

## 6. 数据模型

### 6.1 Club 扩展字段

- `activityTime`：活动时间。
- `weeklyHours`：每周投入小时数。
- `campus`：校区或地点。
- `fee`：费用。
- `skillRequirement`：技能门槛。
- `isRecruiting`：是否正在招新。

PoC 可继续使用字符串标签；生产演进时再拆分标签关联表。

### 6.2 RecruitmentIntent

- `id`
- `clubId`
- `source`：`matching`、`browsing` 或 `chat`
- `matchScore`：可为空
- `sessionId`：匿名会话标识
- `createdAt`

PoC 不收集姓名、手机号和学号。相同会话对同一社团的重复意向应去重。

### 6.3 AIRequestLog

- `useCase`
- `provider`
- `model`
- `status`
- `durationMs`
- `inputTokens`
- `outputTokens`
- `fallbackUsed`
- `errorCode`
- `createdAt`

该表不保存完整 Prompt。

## 7. API 与错误协议

核心新增接口：

```text
POST /api/auth/login
POST /api/auth/logout
POST /api/matching/extract-preferences
POST /api/matching/recommend
POST /api/chat/stream
POST /api/intents
GET  /api/analytics/summary
```

现有 Club 接口保留 REST 语义，更新使用 `PUT`，删除使用 `DELETE`。

所有请求经过服务端验证并使用统一错误结构。主要故障处理：

| 故障 | 用户结果 | 系统处理 |
| --- | --- | --- |
| DeepSeek 超时 | 返回规则推荐 | 记录超时与降级 |
| AI 输出无效 | 返回规则推荐 | 记录 Schema 校验失败 |
| AI 问答失败 | 展示社团搜索结果 | SSE 返回结构化错误 |
| 数据库失败 | 显示服务暂不可用 | 返回 503 |
| 重复加入意向 | 提示已经记录 | 按会话与社团去重 |
| 管理请求未授权 | 显示登录入口 | 返回 401 |
| 输入过长 | 要求缩短输入 | 返回 400 |
| 请求过频 | 要求稍后重试 | 返回 429 |

管理员认证采用 PoC 方案：服务端环境变量配置密码，登录后签发短期 HttpOnly Cookie，所有写接口在服务端校验。README 明确说明生产环境应接入学校统一身份认证和正式 RBAC。

## 8. 测试与验收

### 8.1 自动化测试

单元测试覆盖：

- 各推荐维度的计分和权重。
- 时间、校区、费用和技能等硬约束。
- AI 输出 Schema 校验与非法结果拒绝。
- Token 用量和成本计算。
- 模型错误分类与规则降级。

后端集成测试覆盖：

- Club CRUD 的 REST 方法与响应。
- 未认证用户不能执行管理写操作。
- 推荐结果只能包含真实社团。
- 模型失败时返回规则结果。
- 加入意向提交、去重和统计。
- SSE 正常完成、客户端取消和错误事件。

部署冒烟测试覆盖：

- Docker 镜像能够构建。
- Docker Compose 启动后健康检查通过。
- Nginx 能够提供前端并代理 API。
- 容器重启后 SQLite 数据仍然存在。
- 未配置模型密钥时浏览和规则推荐仍可使用。

### 8.2 最终验收

- 公网演示可以访问。
- 核心流程不包含虚假的成功提示。
- AI 不可用时仍可完成规则推荐。
- 推荐分数、依据和注意事项可以解释。
- 问答真正使用 SSE 流式返回并展示引用。
- 管理写操作受到服务端保护。
- Docker 部署可以重复执行。
- 容器重启后 SQLite 数据仍然存在。
- README 能独立说明业务、架构、成本和取舍。
- AI 指标来自实际评估结果。
- 五分钟内可以完成核心演示。
